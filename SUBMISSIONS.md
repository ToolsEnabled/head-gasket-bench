# Submitting a run

Anyone can submit a run: open a pull request that adds one folder
`runs/submitted/<name>/`. A check runs on the pull request; a maintainer merges
it when the check passes, and the run then appears on the board
(`leaderboard/board.json`).

## 1. Make the run

Use the environment in `env/` exactly as shipped (see `env/README.md`): one
server process per run, a pinned variant (`--variant V1` to `V5`), a new
`--out` folder. Use CPython 3.12; the record names the exact version and is
replayed under the same version. Do not edit any file the environment wrote:
any edit breaks the hash chain and the submission is refused.

## 2. Make the folder

`<name>` is lower case letters, digits, `.`, `_` and `-`, for example
`2026-11-02-model-x-v1`. One run per folder. The folder holds exactly five
files:

| File | What it is |
|---|---|
| `run.json` | the environment's `hgj/run/v2` record, copied unchanged from `--out` |
| `actions.jsonl` | the action journal, copied unchanged |
| `report.json` | the `hgj/repair-run-report/v1` envelope, copied unchanged |
| `SUBMISSION.json` | your declaration (below) |
| `RESULT.md` | generated by the validator (step 3); do not write it by hand |

Leave out `finish-record.json` (for a finished run it is a copy of the record)
and `launch.json`.

`SUBMISSION.json`:

```json
{
  "model_label": "the model as you state it, for example the provider's model identifier",
  "client": "the MCP client and its version, and the effort setting if any",
  "variant": "V1",
  "date": "2026-11-02",
  "submitter": "your name or GitHub handle",
  "notes": "optional: the prompt you used, settings, anything a reader should know"
}
```

All values are strings; `notes` is optional and at most 2,000 characters, the
others at most 200. Nothing else is accepted.

## 3. Generate RESULT.md and validate

From the repository root:

```sh
python3 tools/validate_submission.py --write-result runs/submitted/<name>
python3 tools/validate_submission.py runs/submitted/<name>
```

The validator prints one line, `PASS ...` or `FAIL <folder>: <check>: <reason>`,
and exits non-zero on any failure. It checks, in order:

1. **files**: exactly the five files, regular files, at most 64 MB per record
   file and 64 MB for the whole folder (`RESULT.md` 64 KB, `SUBMISSION.json`
   16 KB).
2. **declaration**: `SUBMISSION.json` is well formed and its variant is V1-V5.
3. **secrets**: no key-shaped strings (API keys, access tokens, private keys,
   bearer credentials) and no personal or machine-local paths (home
   directories, `/root`, `/mnt` and the like) in any of the five files. Tool
   arguments are recorded exactly as your client sent them, so look at the
   files before you submit.
4. **chain**: `run.json` is canonical; every digest matches; the action hash
   chain starts at the configuration hash and links every action; each action
   starts from the previous action's state and the last ends in the final
   state; `actions.jsonl` is exactly the journal; `report.json` names the
   record's SHA-256, score hash and attempt count; at most 1,024 attempts.
5. **pins**: the configuration is one of the five pinned configurations in
   `env/configs/PINS.json` and matches the declared variant; the record was
   made with the current environment runtime and with CPython 3.12.
6. **replay**: `python3 -m headgasket replay` (from `env/`) re-applies every
   action and reproduces `run.json` byte for byte.
7. **scorer**: `scorer/hgj_scorer.py score` accepts the record, agrees with
   the environment's embedded score on every primary checkpoint and on the
   shared bolt, mistake and time fields, and agrees with every row of
   `RESULT.md` (points, S_full, S_partial, failed checkpoints, productive and
   penalty seconds, mistake events, tool attempts, finished, the `run.json`
   SHA-256).

The pull-request check (`.github/workflows/validate.yml`) runs the same
validator on each changed submission, under the CPython version the record
names, using the validator, environment and scorer of the main branch (never
code from the pull request), and checks that `leaderboard/board.json` is up to
date. A submission pull request may change only `runs/submitted/<name>/` and
`leaderboard/board.json`; a pull request that changes anything else is a code
change and is reviewed as one. Rebuild it with
`python3 tools/build_board.py` and commit the result in the same pull request.

## 4. What the board shows

One row per run, as submitted; nothing is averaged.

| Field | Source |
|---|---|
| `name` | `submitted/<name>` |
| `model_label`, `client`, `date` | `SUBMISSION.json`, as you state them |
| `variant` | the record's configuration |
| `points`, `s_partial`, `s_full` | the record's score (the validator has checked it against the independent scorer) |
| `penalty_s`, `productive_s` | charged technician seconds: analyst estimates, not measured labour |
| `source` | `submitted by <submitter>` |
| `exploratory` | `false` for submissions; `true` for the runs ToolsEnabled made before submissions opened |

Rows are sorted by variant, then `s_partial` (highest first), then name. Single
runs describe behaviour; repeats of the same model and variant are welcome and
are what make a result meaningful.

## 5. What ToolsEnabled does and does not verify

ToolsEnabled verifies that the record is internally consistent, replays exactly
under the published runtime, and scores the same under the independent scorer.
**ToolsEnabled does not verify which model served the run**, which client drove
it, how many model calls it took or what it cost: the model label and client
are the submitter's statements and are shown as such. A run that ends without
`finish` is scored as it stands and is listed. By submitting you agree that the
five files are published in this repository under its MIT licence.
