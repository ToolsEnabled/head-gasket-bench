# Submitting a run

Anyone can submit a run: open a pull request that adds one folder
`runs/submitted/<name>/` and the rebuilt `leaderboard/board.json`. A check runs
on the pull request; a maintainer reviews the pull request and merges it when
the check passes, and the run then appears on the board.

## 1. Make the run

Use the environment in `env/` exactly as shipped (see `env/README.md`): one
server process per run, a pinned variant (`--variant V1` to `V5`), a new or
empty `--out` folder outside the repository. Use CPython 3.12: `serve` refuses
any other interpreter, the record names the exact version, and it is replayed
under the same version. A start that makes no tool call (a client's health
check, for example) records nothing.

- **Keep the agent to the job tools.** The repository holds complete correct
  solutions (the scripted records under `runs/` and the reference route inside
  each configuration in `env/configs/`). Start the client in an empty folder
  outside the repository with its own file and shell tools turned off
  (`env/README.md` shows how the baseline did it with Claude Code), and state the
  setup in `notes`.
- **Stop at the budget.** A run has 1,024 tool-call attempts, refused ones
  included. When `turns_remaining` reaches 0, stop calling tools: the environment
  still records any further call, and the pinned independent scorer cannot score
  a record of more than 1,024 attempts, so such a run cannot be submitted (a
  known issue of this environment epoch; the validator says so plainly).
- **Mind `look`.** Each `look` call adds about 0.4 MB to the folder (its result
  of about 200,000 characters is stored in `run.json` and again in
  `actions.jsonl`), so a run with about 150 or more `look` calls is larger than
  the 64 MB a submission may be.
- **Do not edit any file the environment wrote.** The validator re-derives
  `report.json` from the record (only its wall-clock seconds are free), checks
  the hash chain of `run.json` and requires `actions.jsonl` to be exactly the
  journal, so any edit is refused.

## 2. Make the folder

`<name>` is 3-100 characters: lower case letters, digits, `.`, `_` and `-`,
starting with a letter or digit, for example `2026-11-02-model-x-v1`. One run per
folder, and a new run: a record that makes the same tool calls as a published
scripted record or another submission, or that is a withheld ToolsEnabled record,
is refused.
The folder holds exactly five regular files (no links):

| File | What it is |
|---|---|
| `run.json` | the environment's `hgj/run/v2` record, copied unchanged from `--out` |
| `actions.jsonl` | the action journal, copied unchanged |
| `report.json` | the `hgj/repair-run-report/v1` envelope, copied unchanged |
| `SUBMISSION.json` | your declaration (below) |
| `RESULT.md` | generated by the validator (step 3); do not write or edit it by hand |

Leave out `finish-record.json` (for a finished run it is a copy of the record)
and `launch.json`.

`SUBMISSION.json`:

```json
{
  "model_label": "the model as you state it, for example the provider's model identifier",
  "client": "the MCP client and its version, and the effort setting if any",
  "variant": "V1",
  "date": "2026-11-02",
  "submitter": "your name or GitHub handle (shown on the board)",
  "notes": "optional: the prompt you used, the agent's tool access, settings, anything a reader should know"
}
```

All values are strings; `notes` is optional and at most 2,000 characters, the
others at most 200. `date` is a real date written `YYYY-MM-DD`. `model_label`,
`client`, `submitter` and `date` are shown in `RESULT.md` and on the board, so
they must be plain text: no control characters, no bidirectional-override
characters and no backticks. Nothing else is accepted.

## 3. Generate RESULT.md, validate, rebuild the board

From the repository root:

```sh
python3 tools/validate_submission.py --write-result runs/submitted/<name>
python3 tools/validate_submission.py runs/submitted/<name>
python3 tools/build_board.py
```

The validator prints one line, `PASS ...` or `FAIL <folder>: <check>: <reason>`,
and exits non-zero on any failure. It checks, in order:

1. **files**: exactly the five files, regular files, at most 64 MB per record
   file and 64 MB for the whole folder (`RESULT.md` 64 KB, `SUBMISSION.json`
   16 KB).
2. **declaration**: `SUBMISSION.json` is well formed (the rules above) and its
   variant is V1-V5.
3. **secrets**: no key-shaped strings (API keys, access tokens, private keys,
   bearer credentials, web tokens) and no personal or machine-local paths (home
   directories, `/root`, `/mnt`, `/media`, WSL paths and the like) in any of the
   five files, scanned as raw bytes and, for the JSON files you write or copy,
   as decoded strings. The scan cannot catch everything (an e-mail address or a
   host name, for example): tool arguments are recorded exactly as your client
   sent them, so look at the files before you submit.
4. **chain**: `run.json` is canonical; every digest matches; the action hash
   chain starts at the configuration hash and links every action; each action
   starts from the previous action's state and the last ends in the final
   state; 1 to 1,024 attempts; `actions.jsonl` is exactly the journal;
   `report.json` is exactly the envelope the environment writes for this record
   (its status and terminal reason fit the record, and only `real_time.seconds`
   is free).
5. **duplicate**: the tool calls are not those of a published scripted record
   (`runs/family/`, `runs/reference/`) or of another submission, and the files are
   not a withheld ToolsEnabled record.
6. **pins**: the configuration is one of the five pinned configurations in
   `env/configs/PINS.json` and matches the declared variant; the record was
   made with the current environment runtime and with CPython 3.12.
7. **replay**: `python3 -m headgasket replay` (from `env/`) re-applies every
   action and reproduces `run.json` byte for byte.
8. **scorer**: `scorer/hgj_scorer.py score` accepts the record and agrees with
   the environment's embedded score on every primary checkpoint, and on every
   shared bolt, mistake and time field that both scorers determine. The
   independent scorer reports some checklist items as unknown (for example on
   parts a run never touched), and it has one mistake type the environment never
   produces (`missing_timing_verification`, a finished run without a final timing
   check of enough revolutions; the environment scores the same fact in CP11,
   which both decide); neither is compared. `RESULT.md` must be exactly the file
   `--write-result` generates.

The scorer's own `comparison of shared secondary fields` line says
`disagreement` on every record because the two checklists have different item
sets; the validator compares the fields, not that line.

**The pull-request check** (`.github/workflows/validate.yml`) runs on
`pull_request_target` for any pull request that touches `runs/` or
`leaderboard/`. GitHub then takes the workflow file from the main branch, so a
pull request cannot change what its own check runs, and every script the check
runs (the scope check `tools/check_pr_scope.py`, the validator, the environment,
the scorer and `tools/build_board.py`) comes from the main branch. The pull
request's files are read with git and checked out under `pr/` as data only:
nothing from the pull request is executed, imported or installed. The token is
read-only, no secrets are used, and no checkout keeps credentials. The check:

- refuses the pull request unless it only adds new folders
  `runs/submitted/<name>/` of regular files with valid names (a space, a link or
  a stray file cannot slip past) and changes `leaderboard/board.json`; a change
  to anything else, including a published record or a submission already on main,
  is a code change and is reviewed as one;
- runs the validator on each new submission, under the CPython version the record
  names;
- rebuilds the board from the pull request's `runs/` with main's
  `tools/build_board.py` and compares it with the pull request's
  `leaderboard/board.json`.

Maintainers do not merge a submission pull request that changes anything beyond
its `runs/submitted/<name>/` folder and `leaderboard/board.json`, whatever the
check says.

## 4. What the board shows

One row per run, as submitted; nothing is averaged.

| Field | Source |
|---|---|
| `name` | `submitted/<name>` |
| `model_label`, `client`, `date` | `SUBMISSION.json`, as you state them |
| `variant` | the record's configuration |
| `points`, `s_partial`, `s_full` | the record's score (the validator has checked it against the independent scorer) |
| `penalty_s`, `productive_s` | charged technician seconds: analyst estimates, not measured labour |
| `source` | `submitted by <submitter>` |
| `exploratory` | `false` for submissions; `true` for the runs made by ToolsEnabled |

Rows are sorted by variant, then `s_partial` (highest first), then name. Single
runs describe behaviour; repeats of the same model and variant are welcome and
are what make a result meaningful.

## 5. What ToolsEnabled does and does not verify

ToolsEnabled verifies that the record is internally consistent, replays exactly
under the published runtime, and scores the same under the independent scorer.
**ToolsEnabled does not verify which model served the run**, which client drove
it, how many model calls it took or what it cost: the model label and client
are the submitter's statements and are shown as such. Nor can it tell a model
run from a scripted one: the validator refuses an exact copy of a published or
submitted run, but a run that changes a single call is a new record. Every 18/18
submission is therefore reviewed by hand before it is merged. A run that ends
without `finish` is scored as it stands and is listed; a record with no tool
call is refused, since there is nothing to score. By submitting you agree that
the five files are published in this repository under its MIT licence.

Known issues of this environment epoch, which need new pinned code to fix (see
the release notes): a record of more than 1,024 attempts cannot be scored; and on
a run that makes a refused `prepare_condition` or `release_attachment` attempt
during disassembly, the environment and the independent scorer can decide CP02
differently, and the validator then refuses the run, because primary checkpoints
must agree.
